# ERP Posting Bridge 01

## Purpose
Define how ERP modules create accounting impact safely through the existing ledger posting engine.

This document covers:
- business events
- posting intents
- posting profiles
- auto-posting rules
- approval and proposal handoff

## Core Rule
ERP modules must never insert posted ledger rows directly.

All accounting impact must flow through:
1. operational ERP record
2. business event
3. posting intent
4. journal draft or policy-approved auto-post request
5. ledger posting engine
6. immutable posted journal entry

## Design Principles
- ERP modules own operational state, not accounting truth.
- Accounting reports continue to use posted ledger data only.
- Posting behavior must be idempotent.
- Material or risky events must be approval-gated.
- Low-risk auto-posting is allowed only when explicitly configured.
- Every accounting-impacting ERP event must be auditable from source document to journal entry.

## Business Events
A business event is a durable record that an ERP workflow event occurred.

Examples:
- `sales_invoice.issued`
- `sales_credit_note.approved`
- `customer_receipt.confirmed`
- `vendor_bill.approved`
- `vendor_payment.confirmed`
- `inventory_adjustment.approved`
- `fixed_asset.depreciation_generated`
- `payroll_summary.import_approved`

Recommended fields:
- `id`
- `firm_id`
- `organization_id`
- `event_type`
- `source_entity_type`
- `source_entity_id`
- `source_document_number`
- `event_status`
- `event_payload`
- `occurred_at`
- `created_by_actor_type`
- `created_by_actor_id`
- `request_id`
- `correlation_id`
- `created_at`

Suggested statuses:
- `pending`
- `processed`
- `failed`
- `cancelled`
- `superseded`

## Posting Intents
A posting intent is the normalized accounting interpretation of a business event.

It should contain enough information to create a journal draft or post through the ledger engine, but it is not itself a posted journal.

Recommended fields:
- `id`
- `firm_id`
- `organization_id`
- `business_event_id`
- `posting_profile_id`
- `source_entity_type`
- `source_entity_id`
- `intended_entry_date`
- `source_type`
- `memo`
- `status`
- `posting_mode`
- `requires_approval`
- `approval_request_id`
- `journal_entry_draft_id`
- `journal_entry_id`
- `error_code`
- `error_message`
- `intent_payload`
- `created_at`
- `processed_at`

Suggested statuses:
- `pending`
- `draft_created`
- `pending_approval`
- `posted`
- `blocked`
- `failed`
- `cancelled`
- `superseded`

Suggested posting modes:
- `draft_only`
- `approval_required`
- `auto_post`

## Posting Profiles
A posting profile maps one ERP event type to ledger behavior.

Profiles should be tenant-scoped with optional firm templates.

Recommended fields:
- `id`
- `firm_id`
- `organization_id`
- `module_name`
- `event_type`
- `name`
- `description`
- `is_active`
- `posting_mode`
- `debit_account_id`
- `credit_account_id`
- `tax_account_id`
- `discount_account_id`
- `rounding_account_id`
- `journal_template`
- `approval_policy`
- `metadata`
- `created_at`
- `updated_at`

Posting profiles should validate:
- all referenced accounts belong to the same organization
- accounts are active and postable
- required accounts exist for the event type
- posting mode is allowed by module policy

## Auto-Posting Policy
Low-risk auto-posting is allowed, but only through the ledger posting engine.

An event may auto-post only when:
- the organization has enabled auto-posting for that module and event type
- the posting profile is active and complete
- the event is not prior-period or closed-period
- all accounts are active and postable
- the amount is within configured thresholds
- the event has no unresolved document or matching exception
- approval policy returns `allowed`
- idempotency checks pass

Auto-posting should be blocked for:
- prior-period changes
- closed-period postings
- tax or equity account impact unless explicitly allowed
- inventory valuation adjustments
- payroll journals
- fixed asset disposals
- manual override entries
- high-value transactions above threshold
- missing or ambiguous posting profiles
- events generated by low-confidence agent proposals

## Approval And Proposal Handoff
When an ERP event cannot auto-post, the bridge should create a reviewable object.

Possible outcomes:
- create a journal draft and link it to the source ERP record
- create an `agent_proposals` record if the source is agent-assisted or requires review
- create an `approval_requests` record if policy requires approval
- mark the posting intent as `blocked` if profile or validation is incomplete

The approval request should preserve:
- source ERP entity
- proposed accounting impact
- posting profile snapshot
- actor and request metadata
- linked documents
- risk reason

## Reversal And Correction
ERP corrections must not silently edit posted accounting impact.

Recommended behavior:
- operational record can move through module-specific correction states
- previously posted journal entries are reversed through the ledger reversal flow
- replacement events create new posting intents
- audit timeline links original event, reversal, replacement event, and final journal entry

Examples:
- voided sales invoice reverses the original invoice posting
- corrected vendor bill reverses and reposts when accounting impact changes
- inventory adjustment correction creates reversal and replacement adjustment

## Agent Interaction
Agents may:
- inspect ERP records
- prepare posting suggestions
- explain posting profile gaps
- propose invoice, bill, payment, inventory, or depreciation entries
- summarize posting impact

Agents should not:
- bypass posting profiles
- write posted ledger rows
- approve material ERP events
- auto-post events unless policy explicitly allows the same action for the delegated actor

## Error Model
Recommended error codes:
- `POSTING_PROFILE_NOT_FOUND`
- `POSTING_PROFILE_INCOMPLETE`
- `POSTING_PROFILE_ACCOUNT_INVALID`
- `ERP_EVENT_NOT_POSTABLE`
- `ERP_EVENT_ALREADY_POSTED`
- `ERP_EVENT_SUPERSEDED`
- `ERP_POSTING_APPROVAL_REQUIRED`
- `ERP_AUTO_POST_DENIED`
- `ERP_POSTING_INTENT_FAILED`

## Acceptance Criteria
- ERP accounting impact is represented as business events and posting intents before ledger posting.
- Posting profiles are the configurable bridge between operational documents and accounting entries.
- Auto-posting is allowed only when policy and profile both permit it.
- All material ERP accounting impact can be traced to a journal draft or posted journal entry.
- Corrections use reversal and replacement flows instead of mutating posted ledger data.
